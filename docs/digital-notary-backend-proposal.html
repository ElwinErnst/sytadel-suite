Digital Notary Backend Proposal

Project: Sytadel / Secure document workflows

Date: 2026-03-31

1. Objective

The initial Digital Notary backend should certify document existence and integrity, preserve verifiable evidence, and expose a clear API for issuance and verification. The system should not start from blockchain complexity first. It should start from a solid evidence model that later allows different notary providers.

2. What already exists in the current backend

  • DocumentEntity already stores document hashes and anchoring-related state.
  • AnchorService already computes a SHA-256 hash, anchors a document, retries pending operations, and verifies integrity.
  • /public/verify already exposes public verification by documentId.
  • The upload flow already computes sha256PlainHex and persists anchorStatus.

This means the future Digital Notary module does not need to start from zero. The current anchor layer is a good technical seed, but it should evolve into a broader notary model.

3. Recommendation

Do not keep the long-term concept centered around “anchor” only. Use a new Digital Notary module, where anchoring is one implementation strategy or one stage of the evidence lifecycle.

4. Target architecture

  1. NotaryModule
  2. NotaryService
  3. NotaryController for private tenant operations
  4. PublicNotaryController for public verification
  5. NotaryProviderPort to abstract blockchain or external notary providers
  6. NotaryJob / Cron for retries and asynchronous issuance

5. Responsibility split

  • DocumentsService: upload, download, delete.
  • NotaryService: issue certificate, verify evidence, expose history and state.
  • NotaryProviderPort: talk to blockchain or external provider.
  • PublicNotaryController: public verification endpoint.
  • Audit layer: record issuance, verification, retries, and failures.

6. Data model recommendation

Instead of keeping all notary state directly inside documents, add a dedicated table such as notary_records.

Suggested table: notary_records

  • id
  • tenant_id
  • document_id
  • document_sha256
  • status = PENDING | ISSUED | FAILED | REVOKED (optional later)
  • provider = local | ethereum | btc | external
  • provider_ref = transaction hash or external proof ID
  • issued_at
  • verified_at
  • payload_json
  • created_by
  • failure_reason
  • created_at
  • updated_at

Keep only a summary on documents, for example:

  • notary_status
  • latest_notary_record_id

Why this is better

  • A document may need more than one certificate.
  • Evidence history stays independent from document storage concerns.
  • You can reissue, migrate provider, or keep multiple proof records.
  • The system becomes more maintainable and future-proof.

7. Initial API surface

Private endpoints

  • POST /notary/documents/:id/issue
  • GET /notary/documents/:id/status
  • GET /notary/documents/:id/records
  • POST /notary/documents/:id/retry

Public endpoints

  • GET /public/notary/verify?documentId=...
  • Later improvement: GET /public/notary/verify/:recordId

8. MVP workflow

  1. A document is uploaded.
  2. The backend calculates the SHA-256 hash.
  3. A notary_record is created with status PENDING.
  4. A job or manual trigger tries to issue the certificate.
  5. The provider returns a reference.
  6. The record moves to ISSUED.
  7. Public verification uses the saved evidence and the current document hash.

9. Provider abstraction

The first implementation should not be a real blockchain provider. It should be a real contract with a dummy provider. That gives a stable backend surface without locking the project into one anchoring technology too early.

Suggested port

export interface NotaryProviderPort {
  issueCertificate(input: {
    tenantId: string;
    documentId: string;
    sha256Hex: string;
    metadata?: Record<string, unknown>;
  }): Promise<{
    provider: string;
    providerRef: string;
    issuedAt: Date;
    payload?: Record<string, unknown>;
  }>;

  verifyCertificate(input: {
    providerRef: string;
    sha256Hex: string;
  }): Promise<{
    valid: boolean;
    checkedAt: Date;
    details?: Record<string, unknown>;
  }>;
}

10. Minimal states

  • PENDING
  • ISSUED
  • FAILED

These are enough for the first useful version.

11. Authorization model

  • OWNER / ADMIN: issue and retry certificates.
  • MEMBER: read status and record history.
  • Public: verify by public endpoint.

12. Audit events

  • NOTARY_ISSUE_REQUESTED
  • NOTARY_ISSUED
  • NOTARY_VERIFY
  • NOTARY_FAILED
  • NOTARY_RETRY

13. What not to build yet

  • Revocation workflows
  • Complex legal versioning
  • Signed PDF certificates
  • Multi-chain support
  • Custom smart contracts from day one
  • Human notary workflows

14. Recommended implementation plan

  1. Create NotaryModule and notary_records.
  2. Wrap or evolve the current AnchorService into NotaryService.
  3. Create NotaryProviderPort.
  4. Implement DummyNotaryProvider.
  5. Expose private and public endpoints.
  6. Connect retry job / cron.
  7. Later swap the dummy provider for a real blockchain or external provider.

15. Final recommendation

Do not start from “blockchain backend”. Start from a clean evidence backend. If the evidence model and provider contract are solid, blockchain becomes one implementation detail instead of the center of the architecture.
